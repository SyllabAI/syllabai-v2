## Security posture (why this cannot leak)

- No auth bypass exists: the demo session IS a normal login (same
  AuthController/v2 endpoint, same JWT, same RBAC). Every dashboard call
  rides the demo account's own bearer token exactly as any user's would.
- Credentials live in ONE server-only module ("server-only" imported;
  never in a client bundle; import graph verified: the client landing
  does not import it). Env-var names are pre-wired for the removal round.
- The route answers 404 the moment SHOWCASE_DEMO_ENABLED=false — one line
  turns the whole showcase off; full removal deletes 4 files + the graft.

## Ops change of record (the "perpetually" half)

- Live test of record: both demo accounts authenticate against the v2 API
  carrier (roles STUDENT / TEACHER observed on the UserView); token TTL
  observed 7200s = the PT2H default — a static demo session would die
  mid-showcase and bounce visitors to /login.
- Change: SYLLABAI_JWT_TTL=P30D on the API carrier project env (production
  + preview) + carrier redeploy. Rationale: matches the hub's existing
  30-day signed routing cookie (SESSION_TTL_SECONDS), so the "logged in"
  story is true for the whole showcase window. Reversible: remove env,
  redeploy; all other users' next login picks the same 30d posture
  (pilot-consistent, disclosed to the operator in the run report).
