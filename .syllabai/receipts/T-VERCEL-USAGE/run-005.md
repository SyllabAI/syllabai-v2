## Cause (first-hand, run-004's dispatch)

The dispatched bake (run 42366210560) skipped because the idempotence read (`limit=1`, no state filter) picked the newest production deployment **regardless of state** — an in-flight BUILDING for the same sha. Correct outcome in that instance, but the same blindness to state means an **ERROR** (or CANCELED) newest deployment would suppress every future bake while the alias stays old — fail-closed toward a frozen site, violating run-002's law.

## Fix (`.github/workflows/t-vercel-usage-bake.yml`, read step only)

State-aware read over `limit=5`: pick the newest deployment whose state ∈ {READY, BUILDING, QUEUED, INITIATING}; ERROR/CANCELED newest entries are ignored. Semantics: an in-flight HEAD build still suppresses a duplicate bake; a dead newest can never freeze the floor; all-dead/empty → sha='' → bake. Both step outputs (`sha`, `state`) land in `$GITHUB_OUTPUT`; the log line prints the chosen state.
