## The verification that found the blockers (production, live)

1. **The domain itself was healthy from the start.** DNS for
   `www.syllab-ai.com` → Vercel anycast (64.29.17.1 / 216.198.79.1);
   apex `syllab-ai.com` → 308 → www; `GET /` → 200 and the landing
   fingerprint matched (SyllabAI Hub title, `aignite-2026-badge.png`
   preload). Vercel project domains endpoint: both names `verified: true`
   on `prj_YhOJvdlHn1RggYyPKF8ydvvLn6Bl`.
2. **Blocker 1 — CORS.** The demo mint (`GET /api/demo/login?role=…`) and
   the routing mirror (`POST /api/session`) are same-origin hub routes and
   worked; the student bearer token verified against the API carrier
   (200, `hussaina269a@gmail.com`, STUDENT). But every CLIENT-side fetch
   to `https://syllabai-v2.vercel.app/api/v1/*` failed: the CORS preflight
   (`OPTIONS …/learners/me/courses`, `Origin: https://www.syllab-ai.com`)
   returned **403**, while the old hub origin returned 204. The API's
   `SYLLABAI_CORS_ORIGINS` env carried only
   `https://syllabai-hub-v2.vercel.app` — the allowlist predates the new
   domain. Consequence, observed live: the dashboard rendered but the
   roster reconcile (`useMyCoursesSync` → `api.myCourses()`) silently
   failed its catch ("core unreachable — cache law"), so the dashboard
   showed **"My subjects · 0 — No subjects yet"** while the account held
   5 courses (200 via curl with the same bearer).
3. **Blocker 2 — the cached-prefetch-redirect replay.** With CORS fixed
   (see below), the dashboard rendered "My subjects · 5" — but clicking
   either showcase CTA still bounced to `/login?next=…` BEFORE that, and
   even with a valid cookie the login page's own "Go to my dashboard"
   link bounced onto itself. Network log of record (fresh state, cleared
   cookies): the signed-out landing's quick-nav `<Link>`s prefetch the
   gated routes; the proxy answers each prefetch with the 307
   `/login?next=<path>` — and the App Router caches that redirect under
   the DESTINATION's key (`GET /dashboard?_rsc=…` →
   `GET /login?next=%2Fdashboard 200`). After the click (mint 200 →
   mirror 200), `router.push('/dashboard')` replayed the cached redirect
   — NO new `/dashboard` request at all. A hard document load of the same
   URL always worked. This is domain-independent (it reproduces on
   `syllabai-hub-v2.vercel.app` too); the t-demo lane's verification was
   HTTP-level (cookies + 307/200 checks) and never exercised the real
   click path, so it shipped hidden.

## Lesson for every lane

`router.push` after ANY sign-in that was reached through a page whose
signed-out state prefetches gated routes can replay a cached 307 — the
A-2 awaited-mirror law covers the COOKIE race, not the ROUTER-CACHE race.
Sign-in success paths navigate with `window.location.assign`.
