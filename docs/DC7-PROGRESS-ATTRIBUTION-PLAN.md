## 0. The law of record (spec §3.7, verbatim)

> **3.7 DC-7 - Progress Attribution**
>
> Observed (passes 3-4): each Smart Mark advanced the topic tree visibly (2 to 5 to 7 percent across three parts); an MCQ submission added a green check badge to the question chip, lifted the question-set row to "3%", and lit green dots on the tree; checking a revision note filled the lesson's ring green and opened a partial arc on its subtopic and topic rings; and - the strongest link - checking the note auto-completed the study plan's matching "Revise The Microscope in Cell Studies" task (the task flipped to "Mark as incomplete"), while a single MCQ submit did NOT auto-complete the 45-minute "Practise questions" task. Progress is the product's connective tissue: work on any surface visibly moves the tree, and the plan reads the tree.
>
> Decision. Every progress-bearing act publishes an evidence event, and every progress display is a projection of those events - never a local counter. The marking engine already publishes graded evidence; note-completion checks and question attempts join the same stream. A rollup derives three display levels mirroring the observed ring tree: binary completion on the leaf (a note read, a question answered), a fraction ring on the set or subtopic, and a fraction ring on the topic - with SEPARATE dimensions per resource type (notes versus questions), exactly as the observed product keeps two trees. The study plan subscribes to the rollup with per-task-type thresholds: a Revise task auto-completes when its note is checked; a Practise task auto-completes on a marked-parts threshold (five marked parts is the proposed default), not on a single submit. Mechanics. The learner model already carries topic engagement rows and the intervention layer reads them; the rollup extends the same rows with resource-typed fractions. Rings render on the revision-note and question trees from the rollup; the plan's task list renders from the same projection, so "1 of 4 tasks today" and the tree can never disagree.
>
> Acceptance. (a) Event pin: a marked part, a checked note and a submitted MCQ each move exactly the nodes they should (integration test from event to projection). (b) Threshold pin: the fifth marked part flips the Practise task; the first does not. (c) Consistency pin: dashboard rail copy, plan page and rings agree on the same day's count from one projection.

Roadmap Table 3 row of record: P1 | DC-7 rings and plan attribution (event rollup + ring tree + plan projection) | web trees + dashboard + plan | "Event-to-projection pins; fifth-mark threshold flips Practise".

## 2. Mechanics (what this PR lands — additive-only)

1. **The rollup** (`apps/api/src/services/learner/progress-rollup.ts`, NEW) — the event-to-projection module, pure read, deterministic (injected `now`, ADR-031), node-keyed with server-resolved codes:
   - `buildProgressProjection(sql, learnerId, courseSlug, now)` → `{ nodes: { [nodeCode]: { notes: {done, total, fraction, leafDone}, questions: {done, total, fraction, leafDone} } }, today: { notesChecked, markedParts, mcqSubmitted } }` — three display levels per dimension (leaf binary, subtopic fraction, topic fraction) with SEPARATE notes|questions dimensions, exactly the law's shape. Notes dimension: distinct `revision_note_viewed` rows joined through `revision_note.specPointCodes` → node codes → ancestors via `knowledge_edges`; questions dimension: graded facts (`ai_mark_events` per marked part + `attempts` for MCQ/attempt facts) joined through `question_topics`/`question_spec_points` → ancestors. `today` is day-scoped on the injected clock (the consistency pin's "same day's count").
   - `buildPlanProjection(sql, learnerId, courseSlug, now)` → the per-task-type threshold decisions over the SAME projection: a REVISE task auto-completes when its note is checked; a PRACTISE task auto-completes at `markedParts >= PROGRESS_PLAN_THRESHOLD_PRACTISE` (**5 — the spec's proposed default, pinned as the constant of record**), never on a single submit. No plan tables, no builder UI — the projection is the surface the P2 builder renders.
2. **The routes** (`apps/api/src/routes/learner/progress.ts`, NEW) — `GET /api/v1/learners/me/progress?course=` and `GET /api/v1/learners/me/plan-projection?course=`; the `createLearnerStateRouter` posture verbatim (authz shell first, `getAuth(c).userId`, injected `now`, `buildLearnerProgressRouters(env, opts)` composition); mounted by ONE additive line in `apps/api/src/index.ts` at the existing `/api/v1/learners/me` band.
3. **The hub consumes the projection when the learner is signed in** — `lib/progress.ts` gains an additive server-projection loader (fetch the projection; cache per course in memory); `progress-ring.tsx` + `topic-tree.tsx` render projection fractions when present and fall back to the SIMULATED overlay only when signed out (the signed-out posture and its labels are the of-record demo behaviour, unchanged). The flashcard slice of the ring is outside the law's two dimensions (notes | questions) and stays as shipped; folding it into the projection is a disclosed residual (§5).
4. **The dashboard day-count** — a measured-fact line (today's counts from the projection) rendered additively on the dashboard, separate from the recommendation card (its never-mixed law is preserved); acceptance (c)'s three consumers (rings, plan projection, dashboard copy) read ONE payload shape.
5. **No changes**: `prompt.ts` / PROMPT_VERSION (identity of record stays `tutor-grounded/v15`), `packages/contracts/**`, `packages/db/**` (no migration — §1), both fence anchors, the CLA route plane, the recommendation card's contract.

## 3. Acceptance → pins mapping

- **(a) Event pins** (`apps/api/test/learner/progress-rollup.test.ts`, the repo's fakeSql module-pin harness as of record in `engagement-recorder.test.ts`): a marked part (canned `ai_mark_events` + identity rows) moves EXACTLY its question's topic + spec-point nodes and their ancestors and nothing else; a checked note (canned `revision_note_viewed` + `revision_note.specPointCodes`) moves exactly the note's nodes; a submitted MCQ (canned `attempts` AUTO_GRADED row) moves exactly its nodes. Each pin asserts the projected fraction delta and the untouched siblings.
- **(b) Threshold pin**: the plan projection over 1..4 marked parts keeps PRACTISE open; the 5th flips it complete (constant `PROGRESS_PLAN_THRESHOLD_PRACTISE = 5` asserted); a REVISE task flips on its note-check fact alone; a single MCQ submit alone never completes PRACTISE (the observed product's strongest link, pinned verbatim).
- **(c) Consistency pin**: rings payload, plan projection payload and dashboard day-count are derived by the same builder over the same event rows and the same day boundary — the test asserts the three projections' `today` counts are byte-equal from one build call.
