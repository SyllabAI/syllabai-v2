## 0. The law of record (spec §5.3 + Table 3, verbatim)

Table 3 row of record (p211–214 of the extract; header order Phase | Item | Surface | Gate per the DC-7 reading note):

> P2 | Study plan builder (3 steps, pairing rule, thresholds) | web plan | Generated week from tree; Revise auto-complete; Practise threshold

§5.3 surface law (p163–164, verbatim):

> The plan builder is three steps, each cheap and defaulted: step one pre-selects the learner's courses ("Your plan balances revision across the subjects you pick"); step two defaults each course's exam season (May/June 2028 for an A Level two years out, Summer 2028 for the GCSE) with pickers per course; step three defaults two hours per weekday with add controls for the weekend ("Your plan fits your revision into the time you set"). Generation shows a "Creating your Study Plan" interstitial copy that names a "teacher-designed framework", and the result is a weekly page: a goal card ("Get exam-ready - Your plan covers every topic in time for exams" with the season chip), an Edit plan action, a day strip across October 2026, a "0 of 4" counter with a percent, and per-course task groups. Each group pairs exactly one Revise task (Revision Notes, 15 minutes) with one Practise task (Exam Questions, 45 minutes) per topic, each task deep-links into the resource (clicking the revise chip landed on the actual note page), each has an overflow Adjust menu and a complete toggle, and a feature tour overlays the first visit (file 133).

> The attribution behaviour is the finding that matters most for SyllabAI (and is codified in DC-7): after the note check earlier in the session, the plan's "Revise The Microscope in Cell Studies" task rendered in the completed state offering "Mark as incomplete" - the tree wrote the plan, not the learner - while the matching 45-minute Practise task remained open after a single MCQ submit, implying a threshold rather than an event trigger. The dashboard rail then aggregated the same projection ("You've completed 1 of 4 tasks today"). Design take: SyllabAI's plan (a P2 build) should be this projection pattern from day one - tasks derived from the tree with per-type thresholds (Revise = note check; Practise = five marked parts proposed) - and the pairing rule (one short revise, one long practise, per topic) is a sensible default the plan can relax later.

The dashboard rail of record (p162): the right column holds "a Study plan rail ('Structured by experienced teachers, tailored to your courses' with a Create Study Plan button, replaced by today's completion once a plan exists - 'You've completed 1 of 4 tasks today' with a progress bar)".

**Open question (c) resolution of record (spec §6, p175)**: "whether SyllabAI's first plan is deterministic (spec-ordered) or spaced-repetition informed is undecided." Run-001 pins the **deterministic, spec-ordered** generator — the Table 3 gate's own words ("Generated week from tree") and the DC-7 projection pattern are deterministic by construction; spaced-repetition scheduling is a disclosed future relaxation under a new dated prereg, exactly as the spec's design take allows the pairing rule to "relax later". Nothing in this lane measures or claims learning-science optimality.

## 2. Mechanics (what this PR lands — additive-only)

1. **Migration `0012_study_plans.sql`** (CREATE-only, zero bytes on any Flyway-era table): `study_plans` — `id uuid PK`, `learner_id uuid NOT NULL` (+ `fk_study_plans_learner` → users.id ON DELETE cascade), `courses jsonb NOT NULL` (the step-1 selection, ordered array of course slugs), `seasons jsonb NOT NULL` (per-course `{label, examYear, examMonth}`, the step-2 picks), `weekday_minutes int NOT NULL`, `weekend_minutes int NOT NULL` (step-3), `created_at`/`updated_at` timestamptz NOT NULL; `CONSTRAINT uq_study_plan_learner UNIQUE(learner_id)` — ONE active plan per learner (the observed product's single plan; PUT replaces). Check law: `ck_study_plan_minutes CHECK (weekday_minutes >= 0 AND weekend_minutes >= 0)`. Snapshot `0012` (prevId = 0011's id), journal idx 12, schema.ts export, rebaseline pins advanced (measured bump: +1 table, +8 columns, +0 explicit indexes, +1 fk, +1 check, +1 unique → 79/747/107/76/128, uniques 26), README ledger row.
2. **The generator** (`apps/api/src/services/learner/study-plan.ts`, NEW — pure, deterministic, ADR-031 injected clock):
   - `defaultExamSeason(level, now)` — May/June or Summer of `now.year + 2` per the §1 mapping (the spec's "two years out" default; the pickers let the learner change it).
   - `naturalCompareCodes(a, b)` — numeric-aware curriculum-code order of record, unit-tested against the S10/S2 trap.
   - `generatePlanWeek(sql, plan, now)` — per course: `loadUniverse` subtopics in natural order; note-links resolve each subtopic's first note (`note_id` ASC); pairs (REVISE 15 min + PRACTISE 45 min) are laid onto a day walk starting at the plan's `created_at` UTC date — weekday capacity `floor(weekday_minutes / 60)` pairs, weekend capacity `floor(weekend_minutes / 60)`; pairs round-robin across the plan's courses in stored order (step 1's "balances revision across the subjects you pick"); a course's subtopics are consumed in spec order and wrap per cycle — a wrapped subtopic is a REPEAT PASS of the same task (same taskId; the projection guarantees the completion state is identical), which is what the wrap means for a revision plan; counters count slot-instances. The rendered week = the UTC calendar week (Mon–Sun) containing `now`; today's tasks = slots dated `dayStartOf(now)`. **taskId law: `revise:<noteId>` / `practise:<nodeCode>` — byte-identical to the projection's honest-default convention.** Completion: `buildPlanProjection(sql, learnerId, courseSlug, now, weekRefs)` per course — the DC-7 subscription with THIS lane's task list; the payload joins decisions to slots by taskId (repeat passes of one taskId carry one decision by construction).
   - `getStudyPlanDefaults(sql, now)` — registry courses (slug ASC, level/board/label) + per-course default seasons + 120/0 minutes: the three cheap defaults of the three steps.
   - `upsertStudyPlan(sql, learnerId, body, now)` — validate (courses non-empty, every slug resolves in course_registry; seasons keys ⊆ courses, missing courses get the level default; minutes integers 0..600), `INSERT ... ON CONFLICT (learner_id) DO UPDATE` (the unique law), anchor immutability: the day walk always anchors at `created_at` — editing never re-anchors history.
   - The service WRITES only the plan config row. Task completion state is never stored — "the tree wrote the plan, not the learner" is structural (§5 residuals cover the observed manual toggle).
3. **The routes** (`apps/api/src/routes/learner/study-plan.ts`, NEW — posture verbatim from progress.ts): authz shell first; injected `now`; `buildLearnerStudyPlanRouters(env, opts)` composition; mounted by ONE additive `app.route("/api/v1/learners/me", ...)` line in `apps/api/src/index.ts`.
   - `GET /api/v1/learners/me/study-plan` → `{ plan: null }` when none; else `{ plan, week, builtAt }` where `week = { weekStart, weekEnd, today, days: [{date, tasks: [TaskView]}], courses: [{courseSlug, label, season, subtopicCount, cycleEndsOn}], counters: {todayTotal, todayCompleted, weekTotal, weekCompleted, percentToday}, goal: {coversInTime, cyclesNeeded} }`; TaskView = `{ taskId, type, courseSlug, subtopicCode, subtopicTitle, noteId?, minutes, date, complete, autoCompletedBy, markedParts?, threshold? }`. The goal card's "covers every topic in time for exams" claim renders `coversInTime = firstCycleEnd <= seasonDate`; otherwise an honest cycle count (`cyclesNeeded`).
   - `GET /api/v1/learners/me/study-plan/defaults` → the step 1–3 defaults.
   - `PUT /api/v1/learners/me/study-plan` → validated upsert; returns the same shape as GET (fresh week).
4. **The hub surface** (additive):
   - `lib/study-plan-client.ts` (NEW) — the progress-server posture: `useStudyPlan()` (per-session cache, signed-out → null), `useStudyPlanDefaults()`, `saveStudyPlan(body)`, `clearStudyPlanCache()`; wire types mirror the API payloads.
   - `app/plan/page.tsx` + `app/plan/plan-client.tsx` (NEW) — the plan surface: no plan → the three-step builder (step 1 courses pre-checked from the learner's saved-course set ∩ registry, falling back to all registry courses; step 2 per-course season pickers defaulted; step 3 per-day hour steppers, two hours per weekday, weekend add controls) → the "Creating your Study Plan" interstitial naming a teacher-designed framework → the weekly page: goal card with season chip, Edit plan action (back to step 1, config prefilled), day strip, "N of M" counter with percent, per-course task groups with the paired Revise (15 min) / Practise (45 min) tasks; deep links: Revise → `/courses/<slug>/revision-notes/<noteId>` (the observed "clicking the revise chip landed on the actual note page"), Practise → `/courses/<slug>/exam-questions`. Tasks render complete/incomplete strictly from the payload's projection decisions; auto-completed tasks show their provenance (`autoCompletedBy`).
   - `dashboard-client.tsx` — ONE additive Study plan rail block in the right column above "Jump back in": plan absent → "Structured by experienced teachers, tailored to your courses" + Create Study Plan button (→ `/plan`); plan present → "You've completed N of M tasks today" + progress bar + link to `/plan`. Signed-out → the rail renders the copy + button linking to login (the dashboard's own signed-out posture). The recommendation card's contract is untouched; the DC-7 attribution card is untouched.

## 3. Acceptance → pins mapping (the Table 3 gate: "Generated week from tree; Revise auto-complete; Practise threshold")

- **Generated week from tree** (`apps/api/test/learner/study-plan.test.ts`, the repo's fakeSql module-pin harness): fixed now + canned registry/nodes/edges/notes rows → the week's tasks are exactly the spec-ordered subtopic pairs of the plan's courses, round-robin across courses, capacities honoured (120/0 → 4 tasks on a weekday, 0 on a weekend day), day walk anchored at `created_at`, today = the injected day's slice; natural-order pin: a 12-unit course sorts S2 before S10; determinism pin: two builds on the same clock return byte-identical weeks; the taskIds match `revise:<noteId>`/`practise:<nodeCode>`.
- **Revise auto-complete** (the DC-7 subscription, re-pinned through the builder): the generated REVISE ref flips `complete` when its note's `revision_note_viewed` row exists (`autoCompletedBy: "NOTE_CHECK"`) and not otherwise — through `buildPlanProjection`, never a local counter.
- **Practise threshold** (same subscription): 1..4 marked parts keep the PRACTISE task open; the 5th flips it (`autoCompletedBy: "MARKED_PARTS"`, `threshold: 5`); a single MCQ submit alone never completes it (the observed product's strongest link, pinned through the builder's task list).
- **Counter consistency** (the DC-7 acceptance (c) law extended): the rail's "You've completed N of M tasks today", the plan page's "N of M" and the payload's `counters` derive from ONE `generatePlanWeek` build over the same projection — the test asserts `todayCompleted/todayTotal` equal the day slice's decision census.
- **Upsert + validation pins**: PUT with an unknown course slug → 400; empty courses → 400; minutes out of 0..600 → 400; double PUT → one row, updated config, unchanged anchor (`created_at` byte-stable); unique(learner_id) enforced.
- **Defaults pin**: `GET /study-plan/defaults` returns registry courses slug-ASC with the level-mapped seasons (A-Level → May/June `y+2`; IGCSE → Summer `y+2`) and 120/0 minutes.

## 5. Honest gaps & residuals

- **The manual complete toggle and the Adjust menu are NOT in run-001.** The observed product offers both; the spec's design take for SyllabAI pins the projection pattern ("the tree wrote the plan, not the learner") and run-001 lands exactly that. A manual toggle is a plan-state write path (a second truth beside the projection) — it takes its own dated decision; disclosed, not silently dropped.
- **The feature tour overlay** (file 133) is demo chrome, not the law; deferred.
- **Multi-note subtopics** render ONE Revise task (the first note, `note_id` ASC); surfacing per-note revise tasks relaxes the pairing rule exactly as the spec's design take anticipates — future dated prereg.
- **Practise deep link** lands on the course's exam-questions surface (the page's searchParams of record has no subtopic key); a subtopic-scoped question deep link is a residual for the question-rail lanes.
- **Wrap cycles** repeat a course's subtopics after exhaustion (the goal card discloses `cyclesNeeded`); a wrapped subtopic renders as a repeat pass of the same task on each scheduled day (same taskId, one projection decision) — subtopic-starved plans therefore show small repeating task sets, honestly.
- **The flashcards dimension** stays outside the projection (the DC-7 residual, unchanged); **signed-out learners** get the rail copy + login CTA (the dashboard's own signed-out posture); **server-side generation** recomputes the week per read (no task rows — the config row is the only state).
- **Spaced repetition** (open question (c)) is deliberately undecided-and-unclaimed: the deterministic spec-ordered generator is the of-record run-001 posture; any SRS shape is a new operator word + new dated prereg.
